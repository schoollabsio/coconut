# Hashline editing — the shipped design

`propose_edit` addresses lines by **hash**: `read` prints a short digest in front
of every line, and an edit names that digest instead of a line number or a block
of text to match. This document records the design as implemented; the code is
authoritative.

## Why

Both earlier schemes failed silently in ways the agent could not see:

- **Exact `oldText` matching** cannot address a duplicate line at all — with
  `let total = 0;` appearing twice, "replace the first occurrence" is a coin
  flip on which line the user ends up approving.
- **Line numbers** are correct the moment they are written and wrong by the time
  the third edit in the same batch lands, because an earlier edit that inserted
  or deleted above them moves every subsequent target.

A digest of the line's own content fixes both: it identifies one line's text
wherever it sits, and it goes stale in a *visible* way — a line that changed has
a different hash, so the anchor stops resolving and the tool errors instead of
editing something else.

## The hash

- SHA-256 over the line's UTF-8 bytes, one trailing `\r` stripped so CRLF files
  hash like LF ones.
- Five bits per output character from consecutive digest bytes, rendered in
  **Crockford base32** (`0123456789abcdefghjkmnpqrstvwxyz` — no `i`, `l`, `o`,
  `u`, which get mistyped when copied).
- 4 characters by default (32⁴ ≈ 1M buckets; ~4% chance of one collision in a
  1000-line file, and a collision is an *error*, not a wrong edit), accepted up
  to 12 so a longer hash can narrow an ambiguous match.
- Matching is by **prefix**, so `k7qm` and `k7qmhb2f…` address the same line.

## The edit shape

| Edit | Effect |
| --- | --- |
| `{ hash, newText }` | replace that line |
| `{ hash, endHash, newText }` | replace the inclusive range (`endHash` ≥ `hash`) |
| `{ hash, insert: "before" \| "after", newText }` | insert beside the anchor |
| `{ hash, newText: "" }` | delete the line(s), newline included |
| `{ oldText, newText }` | legacy exact match, first occurrence |
| `{ oldText: "", newText }` (sole edit) | create / overwrite the whole file |

Resolution rules, all of them loud failures: unknown hash ("the file changed
since you read it"), ambiguous hash (names every candidate line), malformed hash
(alphabet or length), `endHash` before `hash`, `insert` combined with `endHash`.
Identical duplicate lines are ambiguous at *every* hash length — no digest can
tell two identical lines apart, so the agent must widen the range or use the
legacy mode.

Replacements inherit the line ending of the last replaced line (of the anchor,
for inserts); a file without a trailing newline does not gain one. A `newText`
terminated by `\n` writes the same number of lines, not an extra blank one.

## The read hash column

`read` annotates its own output (pi's built-in `read` returns raw joined lines,
so Coconut's override post-processes the result):

```
1  | // Top-level entry point for the frontend application.
2  k7qm | import { useEffect, useMemo, useRef, useState } from "react";
```

Line 1 prints the **full** digest as a calibration sample, so the exact padding
width is visible before any hash is copied. The column is a display layer: a
notice line (`File not found: …`) never gains one, a content line that happens to
look like a notice always does, and hashes for a window are the hashes of the
same lines in the whole file (truncation never shifts addressing). `hashes:
false` returns raw content.

## Parity: TypeScript ↔ Go

The extension applies edits; the Go backend resolves the *same* anchors to render
the diff the user approves. If the two halves disagreed, the approved diff would
not be the written bytes. So:

- `pi-extension/hashline.ts` and `internal/core/hashline.go` implement one
  contract, documented in the header of the TypeScript file.
- `testdata/hashline_golden.json` pins it: generated by
  `pi-extension/hashline-golden.ts`, asserted by both `go test ./...` and
  `bun test pi-extension/`. Edit either implementation and one of the two suites
  goes red.

## Files

| File | Role |
| --- | --- |
| `pi-extension/hashline.ts` | the contract: hashing, resolution, line ops, `withHashColumn` |
| `pi-extension/hashline.test.ts` | bun suite, incl. golden parity and display edge cases |
| `pi-extension/coconut.ts` | `propose_edit` schema + dry-run resolution; `read` hash column |
| `internal/core/hashline.go` | Go mirror of the contract |
| `internal/core/hashline_test.go` | parity, resolution, edit ops, approval-diff tests |
| `internal/core/diff.go` | `applyEdits` dispatches hashline vs legacy; renders the diff |
| `testdata/hashline_golden.json` | the shared vector both languages must match |

## Notes

- The line-range prototype (`startLine`/`endLine`) that briefly existed in the
  working tree is gone; it had the same "the agent must know it" problem as
  `oldText` plus the shift hazard, and nothing read those fields but the docs.
- `read` output grows roughly 9 characters per line while the hash column is on.
  `hashes: false` is the escape hatch for large reads.
- pi loads extensions with jiti, so `coconut.ts` can import the sibling module;
  `scripts/build-sidecar.sh` copies both files next to the sidecar.
