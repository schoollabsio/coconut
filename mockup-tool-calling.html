The structural fact that dominates the design space: after normalization the UI holds no tool arguments, no tool output and no timings. Every "show me more about this call" idea either needs a protocol addition (D13) or has to live inside {tool,label,path,what,why,status,groupLabel}.

§4 Findings

Chat timeline rows — chat/ToolRow.tsx

IDSymptomCause / code
F1 Every row is the agent's sentence, so the timeline reads like prose and tool identity is invisible. label ("Read ToolRow.tsx") is computed and then never shown. const displayText = call.what || call.label — what is required on every schema (and auto-filled), so label is dead in chat.
F2 The tool-output stream is emitted and silently discarded. applyStreamPayload() handles AgentThinking and AgentToken only — Stream.ToolOutput has no branch, while normalize.go emits it eagerly.
F3 A long run gives zero feedback: no partial output, no elapsed time. consequence of F2 plus no timing on ToolCall.
F4 No result at the end either — no exit code, match count, or lines read. EvAgentToolCompleted = {toolCallId, toolName, status}.
F5 Failure = a red dot with no explanation; the user guesses or asks. error text travels only in the output stream that F2 drops.
F6 A dismissed proposal ends up looking exactly like an applied one. cmdApprovalRespond restores running for both decisions; tool_execution_end then marks it done.
F7 Nothing about progress or outcome while running — the dot pulse is the only signal. ToolRow is one <button> → focusToolCall / focusApproval.
F8 ⤢ detail is invisible until hover/focus, and there is no inline expansion at all. opacity-0 group-hover:opacity-100.
F9 The why — the field we require on every call — is a native tooltip on a truncated line. title={call.why}.
F10 Rows are one-line truncated, so long what strings lose their tail. truncate + the fixed pb-[22px] rhythm.

Grouping — toolGrouping.ts · chat/GroupRow.tsx

IDSymptomCause / code
F10b A group header is a sentence the agent invented ("Review tool calling UI code") plus a bare count — no status rollup, no breakdown, no "4 files read · 1 grep · 2 edits". agentGrouper.formGroup uses the raw groupLabel as the label; GroupRow prints {label} {n} calls.
F12 A pending approval can be invisible. Approval cards only render for rows that exist, and a group's children only render when expanded — collapse the live group and a request is reachable only via the panel chip, which shows the first pending. pushGroupRows: if (!expanded) return; only the newest group auto-expands.
F13 A pending call whose approval vanished shows a done dot in warn text. markerClass() has no pending_approval case; only CallRow checks status and approval presence together.
F11 Expansion is ephemeral local state; the newest group always re-expands itself, older ones never restore. expandedGroups is a Set in the store, never persisted.
F14 Groups shatter on any interleaved assistant text (reads split by a paragraph never collapse), while a 40-call group renders 40 rows once expanded — no cap, no virtualisation. buildTimeline flushes pendingTools on every message atom.
F14b Only two strategies exist: ≥2 consecutive reads, or ≥2 calls with an identical normalised groupLabel. _default counts as "no label", so unlabeled mixed batches (grep + find + ls) each get their own line. normalizeGroupLabel('_default') === ''; defaultGroupers = [agentGrouper, readGrouper].

Approvals — chat/ApprovalCardRow.tsx · content/ApprovalView.tsx

IDSymptomCause / code
F15 The card says Approval needed · propose_edit and · bash — a raw tool id for one, a stale name for the other (the tool is run). ApprovalKindProposeEdit = "propose_edit", ApprovalKindBash = "bash"; the card prints kind verbatim.
F16 The chat card is not decidable: for propose_edit there is no diff, no path, no edit count — you must click through. For run there is a command but no cwd and no "why this needed approval". the card renders kind / what / why / command and nothing else.
F17 The panel approval view is What/Why/Diff/two buttons — no file summary, no edit-by-edit list, no folding of unchanged context, no virtualisation (a 400-line diff renders 400 nodes), no visible keyboard hint. ApprovalView + DiffView (a plain split('\n').map).
F18 With N pending approvals you can only ever reach #1: the panel falls back to pendingApprovals[0] and the chip focuses approvals[0]. No queue, no next/prev, no count in chat. resolvePanelView / PendingChip.
F19 Approve is the only "yes": no approve-with-edit, no approve-rest-of-group, no session-scoped auto-allow ("allow reads this session", "always allow go test") — the whitelist hint literally tells you to go edit settings. the decision is binary (allow/dismiss); the whitelist comes from DEFAULT_READ_ONLY + COCONUT_BASH_WHITELIST.
F20 Sending any message dismisses every pending approval, silently and in bulk — and the timeline keeps no trace of it (F6). Chat.send() → dismissPendingApprovals(client, pendingApprovals).
F21 ⌘⏎ targets focused ?? first with no visible indicator when the panel is showing something else. pickApprovalToRespond.
F22 No age / "waiting since" on a request — a stale request sits forever with no indication of how long. ApprovalRequest carries no timestamp.
F23 Approval card styling is a hand-written CSS island while the panel views are Tailwind — two places to change when the approval look moves. index.css (.approval …) vs Tailwind in the two components.
F24 Dismissing carries no reason: pi is told only "the user dismissed this… do NOT retry", so the user's actual objection is lost — unless they type a message, which triggers F20. the dismiss text in coconut.ts; there is no dismiss-with-note path.
F24b A show_content call appears as a chat row whose text is the auto-filled "Display document X" and promotes the doc into the panel — one action, two artifacts, one of them noise. prepareArguments default what + promoteShowContent.

Data the UI is allowed to show — protocol

IDSymptomCause / code
F25 The tool-detail panel restates the row's fields; nothing in the app can show output, args or results because they were never carried. ToolCall{id,seq,tool,label,path,what,why,status,approvalId,groupLabel} — no output / args / duration / dismissed.
F28 Focus is strictly exclusive — approval, tool and pinned content each clear the others, so you cannot keep a diff open while inspecting a call, or pin a doc next to a pending request. store.focusApproval / focusToolCall / pinContent all null out the other two ids.
F29 Approval summaries (files touched, edit count, +lines/−lines) can't be rendered without re-parsing the diff string. ApprovalRequest{kind,title,toolCallId,path,what,why,diff,command} — the diff is the only structure, and it is a string.
F30 Display naming lives in Go only (toolLabel() → "Edit", "Show", "Run"); the TS layer has no counterpart, so the UI cannot name a tool consistently. normalize.go:toolLabel vs nothing reusable in frontend/src.
F31 The output stream is emitted even though nothing consumes it — bandwidth and memory for a dead path. normalize.go:161 → emitStream(StreamToolOutput).

§5 Decisions to settle before implementation

Each of these is a real fork, not a detail, and several block each other. Answer them out of order — D13 (protocol budget) gates D2–D4, D5 gates D6 and D12.

#QuestionOptions / tension
D1What is a row's headline? (a) tool identity + target, the agent's what demoted to a second line or hover — fixes F1, keeps scanning fast; (b) keep what as headline and add a tool chip + path — keeps the rationale prominent; (c) always two lines — most legible, roughly 2× vertical space per call, which is exactly what the grouping system exists to avoid.
D2Where does tool output belong — chat, panel, or both? Wiring Stream.ToolOutput into the store is cheap (F2). The decision is where it renders: an expandable well under the row, a panel-only detail (F25), or chat for run only. Second half: keep full output per call in memory, or cap it (last N bytes)? Transcripts get long.
D3How loud is a failure? A red dot is not enough (F5). First error line inline in danger text? A new agent.tool.failed event with a message field? A notification? And must a failed (or pending) call escape a collapsed group so it can't be hidden (F12)?
D4Do we add a real terminal state for dismissed calls? A new ToolDismissed status (protocol + normalizer + dot), a dismissed flag on the tool call, or a separate approval-decision record. This is what makes F6 and F20 honest — and it decides whether "3 dismissed" can appear on a group header.
D5Approvals: one queue, or cards in place? Today it's both (chat card + stealing panel) with no queue (F18). Options: a real queue with 1/N and next/prev; stack all pending cards at the tail of the timeline; or keep cards inline and let the panel follow focus only. Decide separately whether a pending approval must bubble to a collapsed group header (F12).
D6Where does the diff live? Is the chat card decidable (a compact ~8-line diff plus "open full diff", so the panel becomes optional), or deliberately a peek that always defers to the panel (F16/F17)?
D7Is auto-allow a first-class UI action? "Allow this prefix this session", "Allow all reads/greps this session", "Add go test to the whitelist" (writes settings → sidecar restart). Cheap and high-leverage; needs a stance on session-scoped vs persisted, and on how it's revoked.
D8Dismiss semantics + note Keep dismiss silent (F24), or add dismiss-with-note that feeds the objection back into the tool result so the agent actually learns? And does sending a message dismiss all (F20), only the focused one, or none at all (just leave them queued)?
D9Grouping rules and header content Keep the two groupers, or add collapse by tool family (search / read / ls), by time window, or by groupLabel across interleaved text (F14)? What should a header say — label, tool breakdown, status counts, "1 error · 2 dismissed"? Should expansion persist per session (F11)?
D10One source of truth for status visuals Adopt toolStatusDotClass everywhere and delete ToolRow.markerClass; fix the final palette per status (running / done / error / pending / dismissed) and decide whether the rail dot and panel dot must match exactly (§3, F13).
D11Panel focus model Exclusive today (F28). A stacked panel (approval on top, tool detail under), tabs, or keep exclusive but stop clearing contentPinned when a tool call is focused?
D12Keyboard model The ⌘⏎ ambiguity (F21): always act on what's visible in the panel, require explicit focus, or add ⌥⏎ = dismiss / ⌘⏎ = approve and print the target inline? Include ⌘Y approve-first and Esc = dismiss?
D13Protocol budget — what we agree to carry Which fields do we add so D2–D4 become implementable: output / outputTruncated / startedAt·endedAt / dismissed on ToolCall; files, editCount, addedLines/removedLines, createdAt on ApprovalRequest. Cost is Go + the protocol.ts mirror + snapshot + store handlers.
D14Do show_content calls belong in the rail? Suppress the row (the panel already shows the doc), or keep a quiet "📄 report.md shown" marker (F24b)?
